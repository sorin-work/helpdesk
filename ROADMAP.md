# Roadmap

Things I might add to helpdesk. The app covers the whole loop for a small team
today (customers open requests in the portal, agents work them from queues
with SLA targets, admins set hours, targets and the team), so nothing here is
promised or scheduled. These are ideas, written down with enough detail that I
(or anyone else) can pick one up later without starting from zero. Items may
change, move between groups or be dropped.

What the app does today is in the [README](README.md) and the notes under
[docs/](docs/).

- **Next**: small or well understood. I would start with these.
- **Later**: worth doing, but bigger or waiting on a decision.
- **Maybe**: not sure yet that they are worth the extra complexity.

Sizes are rough: **S** is an evening or two, **M** a few evenings up to a
couple of weekends, **L** several weeks of spare time.

Each item is meant to fit in one pull request and to be covered by the test
suite. Pure logic (business hours, SLA states, statuses, placeholders) lives in
`api/src/lib` with a unit test next to each file, so new rules worth testing
(rate windows, mail templates, merge rules) belong there, not inside a route.
Route and service behaviour is tested in `api/test/*.test.ts` through
`fastify.inject` against PGlite with the real migrations applied. Web tests use
Vitest and Vue Test Utils next to the file they cover (`web/src/components`,
`web/src/stores`, `web/src/utils`); there are no browser tests yet (item 27).
Schema changes are Drizzle table definitions under `api/src/db/schema` plus a
migration generated by drizzle-kit into `api/drizzle` (the next one is
`0011_...`). File names below are relative to the repository root.

When an item ships, its row in the Overview says `Shipped` in the Group
column, and its section moves under a `## Shipped` heading at the end, cut
down to one paragraph on what was built and anything left out. The same pull
request updates the README, `docs/api.md` (and `docs/sla.md` when SLAs are
touched) and adds an entry under `## Unreleased` at the top of `CHANGELOG.md`.

"Depends on" lists real prerequisites only. Items that merely touch the same
file are not listed there; the bigger overlaps are mentioned in the items.

## Next

### 1. Slow down password guessing

`POST /api/auth/login` and `POST /api/auth/signup` take any number of
requests. The login route also answers faster for an unknown email: when
`findUserByEmail` finds nobody, `verifyPassword` (bcrypt) never runs, so the
response time tells an attacker which emails have accounts, even though the
message is the same.

- `@fastify/rate-limit` on the two routes: for login, five failures per email
  and 20 per client address in 15 minutes, then 429 with `Retry-After` and the
  usual error shape (`{ error: { code: 'rate_limited', ... } }` through
  `api/src/plugins/errors.ts`). For sign-up, a few accounts per address per
  hour.
- Compare against a fixed dummy hash when the email is unknown or the user is
  inactive, so all failures cost the same.
- Tricky: `buildApp` sets `trustProxy: true`, so `request.ip` comes from
  `X-Forwarded-For` whatever sent it. Behind the bundled nginx that is right;
  run without it and any client can pick its own address. A `TRUST_PROXY`
  setting (default: true in compose, false otherwise) in `api/src/config.ts`.
- Tricky: the counter is per process, in memory. The compose stack runs one
  API container; say so in the README.
- `LoginView.vue` shows the 429 message with the wait.
- Tests: in `api/test/auth.test.ts`, the sixth failure gets 429, a success
  resets the email counter, and the dummy hash path is taken for unknown
  emails (spy on `bcrypt.compare`).

### 2. Email notifications

There is no email at all. A customer who opens a request has to come back to
the portal to see whether anyone answered, and an agent has to keep the queue
open to see a new ticket or a customer reply. For a help desk this is the
biggest gap.

- Optional SMTP settings (`SMTP_URL`, `MAIL_FROM`, `APP_URL` for links) in
  `api/src/config.ts`. Without them nothing is sent and the README says so.
  A mailpit container in docker-compose for development, on a free port.
- Customers get: "we received your request" on create, every public reply
  from an agent (never internal notes), and "your request was solved". Agents
  get: a ticket assigned to them, a customer reply on their ticket, and,
  optionally, every new unassigned ticket.
- An `outbox` table (recipient, template, data, status, attempts, sent_at)
  written in the same transaction as the change, and a sender loop next to
  the existing `housekeeping` interval in `api/src/index.ts` that sends and
  retries with backoff. That way a slow or failing SMTP server never fails a
  reply, and a crash does not lose mail.
- Templates as plain functions in `api/src/lib/mail-templates.ts` that return
  subject, text and a simple HTML version, using the ticket number and a link.
  The reply body goes into the mail as text, escaped in the HTML part.
- Per-user settings on the profile page: agents can turn each kind off;
  customers can turn off everything but replies.
- Tricky: loops and noise. Do not mail the author of a reply about their own
  reply; collapse several replies within a minute into one mail per recipient.
- Tricky: deactivated users and the demo seed. Skip inactive users, and do not
  send anything for seeded data (the seeder writes tickets directly).
- Undecided: whether the reply mail quotes the whole thread or only the new
  reply. I would send only the new reply with a link; item 6 will need a
  marker line for replies by email.
- Tests: template unit tests; `api/test/messages.test.ts` checks the outbox
  rows for a public reply and none for a note; a sender test with a fake
  transport for retries.

### 3. Password reset by email

`POST /api/auth/password` changes a known password. A customer who forgot it
has to sign up again with another address, which splits their history, and an
agent has to ask an admin, who cannot set a password either (`PATCH /users/:id`
takes name, role and active only).

- `POST /api/auth/password-reset` always answers 202. For an active account
  it stores a random token's hash with a one hour expiry and mails a link
  through item 2's outbox.
- `POST /api/auth/password-reset/confirm` with the token and a new password
  sets it, marks the token used, and ends the user's other sessions (item 4).
- A "Forgot password?" link on the login page and a small reset view.
- Admins get "Send reset link" on `UsersView.vue`, which also covers agents
  created by an admin without a password they know.
- Tests: expired, reused and unknown tokens; the 202 for unknown emails; the
  rate limit from item 1 applies to this route too.

### 4. Sessions that end when they should

The session is a JWT in an httpOnly cookie, valid for `SESSION_DAYS` (seven).
`/auth/logout` only clears the cookie in that browser, and changing the
password leaves every other session signed in. The per-request user lookup in
`api/src/plugins/auth.ts` already handles deactivation and role changes, so
the missing piece is small.

- A `session_version integer` on `users`, put into the token as a claim at
  `startSession`. `authenticate` already loads the user; it now also compares
  the version and answers 401 on a mismatch.
- Bump it on a password change (keeping the current session by issuing a new
  cookie), on a reset, and from a new "Sign out everywhere" button on the
  profile page.
- Admins get "End sessions" for a user, for a lost laptop.
- Tests: in `api/test/auth.test.ts`, an old cookie fails after a password
  change while the new one works.

### 5. Clean up unused uploads

Files are uploaded first and linked to a message when it is posted
(`linkAttachments`). A file that is uploaded and never sent (the reply was
abandoned, the tab closed) stays on disk under `UPLOAD_DIR` and in the
`attachments` table forever with `message_id` null. Nothing removes files of
deleted tickets either, if ticket deletion is ever added.

- Add the cleanup to the hourly `housekeeping` in `api/src/index.ts`: delete
  unlinked attachments older than a day, file first, row second.
- A second pass, run daily, that lists the storage folders and removes files
  with no row (left by a crash between writing the file and inserting the
  row). `api/src/modules/attachments/storage.ts` gets a `list` and `remove`.
- Tricky: the order on failure. Removing the row first and failing on the
  file leaves an orphan file, which the second pass picks up; the other way
  round leaves a row pointing at nothing, which breaks a download. Row last.
- Tricky: an upload in progress while the cleanup runs. The one day age
  avoids it.
- Tests: in `api/test/attachments.test.ts` with a temporary `UPLOAD_DIR`: an
  old unlinked file goes, a linked one and a fresh one stay.
